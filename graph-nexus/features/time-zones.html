    Time Zones

    This page explains how Nexus displays dates and times and handles time zones.

    About time zones#

    Every geographical region has its own standard time zone. Each zone has a UTC offset, which is the difference in hours and minutes from Universal Coordinated Time.

    Many regions observe Daylight Saving Time (DST), where the time offset changes to accommodate differences during the seasons. Offset rules may also change for unpredictable political reasons.

    Date objects in JavaScript#

    You can create a Date object using JavaScript's built-in constructor:

    // Creating a Date object for the 26th Dec. 2010, 9 AM
var date = new Date(2010, 11, 26, 9, 0, 0);

    The browser knows the operating system's current time zone. It uses this to offer conversions to UTC. For example:

    var hours = date.getUTCHours();

    Most browsers don't allow for changes to time zone rules, so the UTC conversion may not be correct.

    How Nexus handles time zones#

    Nexus displays the literal date and time defined in your code: it doesn't try to convert or standardise them. If you want to control how Nexus works with time zones, choose one of the options below.

    Option One: UTC dates on server and browser#

    If your users work with servers that record dates in UTC, they'll probably want to see their data in UTC too. Construct your JavaScript dates using the times you get from the server directly.

    For example, your server logs have an entry (in ISO 8601 standard) for May 22, 2016:

    2016-05-22T07:58:33.592Z

    You would create a JavaScript Date object:

    // Note months are zero based in JavaScript
var date = new Date(2016, 4, 22, 7, 58, 33, 592);

    To pass this date to the time bar, use an item's dt property. The time bar displays the date 'as seen' - i.e., in UTC.

    Option Two: UTC date on server, local time for the user#

    Your users may prefer to see the local time for a time zone instead of UTC dates from their server. It's best practice to let your users choose their time zone.

    We recommend that the conversion to local time is done on the server before the data is sent. When the data arrives it will already be in local time, so use the standard JavaScript constructor:

    For example, your server logs have an entry (in ISO 8601 standard) for May 22, 2016:

    2016-05-22T07:58:33.592Z

    Convert this to local time - say Eastern Daylight Time (EDT) - on the server:

    May 22, 2016 03:58:33.592

    This is four hours earlier because EDT is 4 hours ahead of UTC. If the date was outside Daylight Saving Time, your conversion would be five hours behind.

    Use a library to help with this conversion, such as Moment.js.

    When the data arrives it will already be in local time, so use the standard JavaScript constructor:
    item.dt = new Date(data.time);

    Your users will now see EDT in the time bar.

    Other options#

    If you don't choose either of these options, you must convert the date to the right time zone before passing it to Nexus.

    Using milliseconds for dates#

    For convenience - and better performance - the time bar API accepts numbers for dates.

    Nexus interprets the value from the number of epoch milliseconds since January 1, 1970, 00:00:00 UTC, and the time bar uses UTC to display the values. This means the time bar displays the same values no matter which time zone the user is in.

    This example would be 3pm May 11, 2015 in UTC - not local time - to users anywhere in the world:

    var ms = 1431356400000;

    To avoid unwanted time zone conversions, we recommend using milliseconds when calling timebar.getIds and timebar.range.

    Note: Date ranges returned by any part of the time bar API ('click', 'hover' and 'pointer-down' events or timebar.range() used as a getter) are in local time. To recover the equivalent milliseconds, use:

    var ms = Date.UTC(dt.getFullYear(), dt.getMonth(), dt.getDate(), dt.getHours(), dt.getMinutes(), dt.getSeconds(), dt.getMilliseconds());
